1. Visão Geral

Propósito

O Outlier OS é um sistema operacional interno construído à medida para a agência Outlier Agency (Daniel Godinho). Serve como hub central de gestão: clientes, tarefas, lançamentos, conteúdo, financeiro, OKRs, processos, reuniões, incubadora de alunos e camada estratégica (iniciativas, mentorias, decisões CEO).

Substitui a dispersão entre ClickUp, Sheets, dashboards HTML soltos e outras ferramentas, centralizando toda a operação e tomada de decisão numa única aplicação web autenticada.

5. Autenticação e Autorização

Como funciona

A autenticação usa Supabase Auth com sessões baseadas em JWT armazenadas em cookies HTTP-only.

  1. O utilizador acede a qualquer rota protegida → Next.js Middleware (middleware.ts) executa updateSession()
  2. updateSession renova o JWT via supabase.auth.getUser() e actualiza os cookies
  3. Se não há sessão válida, redireciona para /login
  4. Se há sessão e o utilizador tenta aceder a /login, redireciona para /dashboard
  5. Rotas /share/* são públicas (sem autenticação)

Roles e Permissões

RoleDescriçãopermissions_modules
admin Acesso total a todos os módulos. O primeiro utilizador a registar fica automaticamente admin (via trigger). [] (array vazio — ignora a lista, acesso total)
membro Acesso apenas aos módulos listados em permissions_modules. Array com keys dos módulos permitidos ex: ["clientes","tarefas"]

-- Verifica se uid tem permissão para módulo específico
-- (admin ignora a lista; membro verifica permissions_modules)

8. Triggers e Funções SQL

Trigger / FunçãoEm que tabelasO que faz
trg_set_updated_at()
Trigger: set_updated_at		 team_members, clients, launches, launch_templates, tasks, contents, students, reports, recurring_transactions, objectives, key_results, processes, meetings, mentorships, initiatives, decisions BEFORE UPDATE — define updated_at = now() automaticamente em qualquer UPDATE.
trg_handle_new_user()
Trigger: on_auth_user_created		 auth.users AFTER INSERT — cria automaticamente um registo em team_members com o nome e email do utilizador. O primeiro user registado fica com role='admin'.
trg_log_activity()
Trigger: log_activity		 clients, tasks, launches, contents, students, objectives, meetings, processes, transactions, initiatives, decisions, mentorships AFTER INSERT OR UPDATE OR DELETE — grava em activity_log a acção (created/updated/deleted), o membro que a fez, o tipo e id da entidade, e um label snapshot (campo name ou title). Em caso de excepção, nunca bloqueia a operação principal.
is_admin(uid) — Função helper SQL (security definer) para uso nas políticas RLS. Verifica se uid tem role='admin' e active=true em team_members.
is_team_member(uid) — Função helper SQL. Verifica se uid existe e está activo em team_members.
has_module(uid, module) — Função helper SQL. Admin retorna sempre true. Para membros, verifica se module está em permissions_modules.

11. API Endpoints

O projecto tem apenas um Route Handler dedicado. Todas as restantes operações usam Server Actions.

POST /api/share/feedback

Ficheiro: app/api/share/feedback/route.ts · Acesso: Público (sem autenticação)

Payload

{
  "clientId": "uuid",    // obrigatório
  "name": "string",     // opcional, máx 100 chars
  "body": "string"      // obrigatório, máx 5000 chars
}

Comportamento

  1. Valida payload (clientId obrigatório, body não vazio e <5000 chars)
  2. Verifica que o cliente existe e tem public_share_enabled = true
  3. Se falhar → 403 Forbidden
  4. Insere em content_feedback com is_from_client=true e read_by_team=false

Usa

createAdminClient() (service_role) — valida o cliente antes das escritas.

15. Segurança — Pontos de Atenção

Edge Functions

✅ O projecto não usa Edge Functions Supabase. Toda a lógica server-side corre via Next.js Server Components e Server Actions, protegidos pelo middleware de sessão. Não existe o risco de Edge Functions sem verificação JWT.

RLS — Verificação por Tabela

✅ RLS está activo e com políticas em todas as 34 tabelas. Confirmado na migration 0002 e 0005. Nenhuma tabela foi encontrada sem enable row level security.
